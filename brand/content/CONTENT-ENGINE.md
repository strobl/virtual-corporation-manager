Make the product account a place to see useful team structures and concrete progress. The repeating editorial unit is one idea, one visual, one next action. The launch queue contains twelve complete posts and a pinned introduction; slots are relative to the account launch, not invented scheduled dates.

Use 09:00 Europe/Berlin as a provisional production time. Posting time is a hypothesis until the account has real analytics. Three useful posts per week are the starting cadence. Prepare each batch before scheduling; avoid filling empty days with paraphrases of the same slogan.

## The production loop

1. Check the repository's current default branch, release notes, public examples and relevant docs. A commit is evidence of a source change; only a shipped release supports a release claim.
2. Pick a topic that has not already been queued or posted. Save its source URL, revision, visual, final text and alt text. Keep pending draft backlog to six during steady state; the launch package is the initial twelve-post exception.
3. Use `brand/source/build.py` to adapt an existing editable master. Keep Rubik Bold, original logo paths, orange/cream/ink and consistent connector geometry. Render with `brand/source/render.cjs`. Review at mobile feed size.
4. Check names, output dimensions, text bounds and the actual claim. Reporting, membership and ownership are different relationships. Configured roles are not executed work; entered delivery hours are not runtime or proven savings. Show synthetic examples as examples.
5. Review the exact account, copy, visual and destination. A draft becomes scheduled only when the platform returns a schedule; a post becomes published only when its public URL is verified. Save those values in the queue.
6. After publication, record real impressions, profile visits, link clicks, replies and subsequent GitHub activity when available. Evaluate each series over four weeks. No invented baseline, followers or results.
