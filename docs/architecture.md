# Architecture

VCM — Virtual Corporation Manager is one TypeScript application for one local operator to create and maintain corporations: their human and AI members, responsibilities, departments, reporting, company relationships and recorded delivery hours. A Node.js process serves a bundled React console on `127.0.0.1` and opens a SQLite workspace. These local management functions require no account, network, hosted database, billing service or telemetry. A human member is a company identity, not another application user.

This describes the `0.1.0-alpha.7` corporation-management technical prerelease, combining the adopted company workspace with VCM naming. The [product contract](product/corporation-management.md) defines the company-centered model. The [system architecture](system-architecture.md) maps its three core containers, components, persisted data and execution flows to source. [Architecture for contributors](developer-architecture.md) explains the domain and change workflow; [acceptance evidence](acceptance.md) records the exact source, package and observed checks separately. Alpha.5 and alpha.6 evidence remains historical.

The primary loop is **Corporations → Create company → Add member → review and save → reopen the company**. [QuickCompanySetup](../src/web/QuickCompanySetup.tsx) needs a name and optional purpose, supplies internal defaults and submits an empty portable definition through the existing preview/apply route. [CorporationWorkspace](../src/web/CorporationWorkspace.tsx) lists companies; [CompanyConsole](../src/web/CompanyConsole.tsx) composes the selected company's roster, member details, departments, reporting, ownership/collaboration and hours summary. Basic management stays in one company context. The existing map, detailed reporting views, agent runs, workflow examples and runtime connections remain secondary tools.

The existing `Agent` contract represents both `kind: 'human'` and `kind: 'agent'`; the UI calls them members. One identity can have primary and additional company assignments. Profile, department and reporting fields belong to that identity, not to independent copies per company. Ownership connects companies and does not model human shareholdings. A human's **Record work** submits manual text through the reviewed work-record command with no runtime ID, duration or automatic hours. Individual runtime admission and workflow-role selection both require active AI agents.

The browser submits typed configuration commands to the local runtime. Domain validation produces a persisted preview at a specific workspace revision. Explicit confirmation applies that exact preview and its audit receipt in one transaction. Replaying confirmation is idempotent; intervening configuration or time writes invalidate stale previews. Supported undo is version-aware and does not reverse an external action. An uncertain Apply receipt survives browser reload for explicit retry. See the [workspace store](../src/db/store.ts), [domain model](../src/domain/model.ts) and [browser recovery](../src/web/change-recovery.ts).

SQLite schema 5 holds organization, changes, work, execution receipts, workflow artifact bytes and a separate delivery-hours ledger. Time writes atomically persist the entry, captured calculation basis, history and request receipt while advancing the shared workspace revision. Totals use integer tenths of a human-equivalent hour. Configuration replacement preserves the time and execution ledgers; elapsed runtime, accepted output and booked hours are separate facts. See the [data model](data-model.md) and [Time Tracker](time-tracker.md).

Creating a member stores its role and assignments; reporting does not delegate tasks and execution requires an explicit task or job. An AI member's **Give a task** opens a runtime confirmation; **Tools → Agent runs & records** retains its output and manual contributions, **Workflow examples** contains fixed jobs, and **Tools → Connections** handles optional runtimes. The individual-task queue runs one task at a time with at most 20 outstanding requests; its Codex route returns read-only text output. A shared agent runs in its primary company, which the UI identifies before dispatch. The fixed PS-001 workflow runs five roles sequentially in separate workspace-write sessions, with one active job and at most three active-plus-queued jobs total. Start and Retry enforce the same admission limit. These queues are separate, so one individual task can run alongside one workflow. Codex uses the operator's installed CLI and provider access; experimental Buzz and Slack routes have additional prerequisites. See [integrations](integrations.md).

PS-001 captures the company, five role identities, named acceptance owner and content/input hashes. A prerequisite check precedes model dispatch. Runtime stages create actual files; a fixed sandboxed Python oracle and a different QA session inspect the captured candidate. Successful handoff leaves an explicit owner decision pending. The ready ZIP is sealed with frozen pre-decision provenance, SHA-256 and byte length; a new accept/reject decision records that exact digest. Downloads remain byte-identical after review and restore. Historical decisions without a bundle hash remain unbound; VCM does not manufacture past attestations. The [workflow contract](product-studio.md) and [workflow service](../src/jobs/service.ts) describe the bounded route.

The runtime owns an exclusive workspace process lock. Its [HTTP boundary](../src/server/index.ts) checks Host, Origin, cross-site requests, asset paths and a random per-process mutation capability. Trusted local processes can retrieve that capability from the session endpoint; it is not a shared-user authentication system. LAN hosting and tunnels are outside the supported deployment model. Data and backups are plaintext with local file permissions; runtime sandboxes restrict writes without promising full read isolation. See [security](../SECURITY.md).

Full SQLite backup/restore preserves configuration, hours, execution evidence and replay receipts together, validating migrations and data before replacement. Definition JSON is configuration only; time JSON is an inspectable ledger export. Completed workflow files survive without their disposable stage directories. Interrupted provider work is not automatically replayed on restart. Recovery commands are in the [developer quickstart](developer-quickstart.md#export-and-recovery).

The package uses Node's built-in `node:sqlite`; supported engines are Node 24.14+ within 24.x and Node 26.x. The local core and Time Tracker support macOS, Linux and Windows. Optional company-workflow checks additionally require Python 3.8+ and a working macOS/Linux Codex sandbox; native Windows is unsupported for that route. Source, configured CI and a built archive each need their own verification before a release claim.

An empty company is a valid starting state; a useful management outcome requires the operator's real members, responsibilities and meaningful edits. Internal fixtures do not establish external management usefulness. Optional execution retains separate acceptance: PS-001 v2 intake and its one retry each timed out after 300 seconds at `ultra`, leaving no v2 bundle or owner acceptance; the earlier v1 download remains rejected for its missing expected-reference file. Live Buzz/Slack outcomes and external human usefulness remain open. The product-model change does not erase those results or authorize another provider attempt.
